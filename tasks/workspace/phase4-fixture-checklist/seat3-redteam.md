# Seat 3 — Red-Team / Validity Threats

**Status:** Draft
**Date:** 2026-06-24
**Captured by:** seat3-redteam (panel session, Phase-4 fixture design)
**Rule:** Measure rework on named, line-addressable design decisions only; blind design-from-stress sessions; normalize by decision-count not word count.

## Ranked Validity Threat Table

| # | Threat | Severity | Bias Direction | Minimal Guard |
|---|--------|----------|----------------|---------------|
| **T1** | **Executor confound — same orchestrator/arm machinery runs BOTH stages** | **H** | Arm A stress session may "protect" its own panel design (pull punches) OR over-rework to simulate thoroughness; Arm B/C stress less inhibited. Net direction is unknowable without measuring it — which means the effect is uncontrolled noise masquerading as signal. | **Mandatory blind cross-arm stress execution.** Design stage: run under normal arm machinery. Stress stage: run under a FIXED vanilla Sonnet (no arm machinery at all — no PRISM hooks, no panel, no `PRISM_PANEL_DISABLED`). The same "stress executor" is used for ALL arms. This removes the arm from the measurement of its own output. |
| **T2** | **Verbosity bias on survival — panel (Arm A) writes longer ADRs with more named decisions, creating more surface for "rework" attribution** | **H** | Directionally ambiguous but asymmetric: (a) more named decisions = more checklist anchors that could each be reworked (harms Arm A), but (b) more explicit decisions = fewer ambiguous spots the stress can silently route around (helps Arm A). Empirically Item 6 showed arm detectability via length, so the effect is real and large. | **Normalize survival denominator to NAMED-DECISION COUNT, not total lines.** Each task's `expected_artifact` already names the concrete decisions (storage model, projection strategy, isolation model, etc.). Checklist items must bind 1:1 to those named decisions only. A 2,000-word ADR and a 200-word ADR that both name the same 4 decisions have the same denominator = 4. Verbosity outside those anchors is irrelevant to the score. |
| **T3** | **Attribution false-negative — stress session writes a NEW file (e.g., a new migration, a new invalidation module) that silently supersedes a design claim without touching the original ADR lines** | **H** | Arm A produces an explicit design; stress adds a parallel design document or code file that contradicts it. git blame on the ADR shows 0 rework. Score = SURVIVED. Ground truth = FAILED. Systematically inflates survival for arms with verbose explicit designs (Arm A) if stress prefers workaround over edit. | **Checklist items must also check for PRESENCE of superseding artifacts.** For each named decision, add a complementary item: "Does any file introduced in the stress session contradict or replace the named decision without modifying the original design file?" This requires a directory scan, not just blame. Guard: harness asserts no new `*.md`, `adr-*.md`, or design-pattern files are created in the stress session except inside a `stress/` directory scoped folder. Any design-scope file written outside that folder is flagged. |
| **T4** | **Attribution false-positive — stress session reformats, renames, or restructures the ADR file (e.g., fixes headings, moves sections) without changing any design decision** | **M** | Reformatting produces git blame churn. Checklist item resolves YES. Score = REWORKED. Ground truth = NOT a design rework. Slightly harms all arms equally, but harms more verbose designs (Arm A) more because there are more lines to touch. | **Checklist items must specify the semantic anchor, not the line number.** Example: "Was the stated cache invalidation strategy (TTL vs CDC) changed in the stress session?" — not "Was line 47 of design.md modified?" Script checks: git diff on the decision value (the string after the named field), not on the surrounding markup. Pre-commit hook on the stress stage should block cosmetic reformatting (enforce `--no-rename`, `--no-reformat` lint pass before commit). |
| **T5** | **Trivial survival — design makes no concrete named decision (vague hedge: "we could use either X or Y depending on context")** | **M** | If the design says "TTL or CDC depending on requirements," the stress cannot rework a named choice because none was made. All checklist items resolve NO-REWORK vacuously. Score = SURVIVED. Ground truth = no design quality at all. Arm C (vanilla Sonnet) is most likely to produce hedged non-decisions. Arm A least likely (panel forces a stance). Biases toward null result (arms converge toward survival). | **Checklist item RC-0 (prerequisite gate): "Does the design name a concrete choice for each required decision in `expected_artifact`? If NO, session is scored as DISQUALIFIED, not as SURVIVED."** This must be computed before the stress session runs so the harness can flag and re-run the design session (within same arm) rather than proceeding to stress. Disqualified sessions are NOT counted in the survival denominator. |
| **T6** | **Ordering / stress-dimension leakage — design session is contaminated by seeing the `stress_dimension` field from tasks-v1.json** | **M** | If the harness passes the full task object (including `stress_dimension`) to the design session, Arm A's panel will pre-empt the stress attack trivially (high survival not due to quality, but to information advantage). Arm C (vanilla) may not use the hint as effectively, creating a spurious gap. | **Harness MUST pass only the `prompt` field to the design session; `stress_dimension` is withheld until session N+1.** Audit the harness prompt-construction code before run 1. Add a pre-flight assertion: run the harness in dry-run mode and dump the full prompt sent to each session — a human must sign off that `stress_dimension` is absent. |
| **T7** | **Trivial failure — design is exhaustive and maximally verbose; stress finds minor nitpick to justify one edit per named section** | **M** | Stress session systematically touches each decision section to "respond to the requirement," producing blame on every anchor. All checklist items resolve YES-REWORKED. Score = FAILED. Ground truth = design was actually high quality and the "rework" was cosmetic elaboration. Most likely to harm Arm A (longest, most explicit designs). | **Checklist items must distinguish CHANGE TO THE NAMED DECISION VALUE from ELABORATION THAT PRESERVES IT.** Example: stress adds "and we now also require flush within 5s" elaboration to an already-correct CDC choice = NOT rework. Rework = the CDC decision is replaced by TTL, or the strategy is reversed. Guard: require that each checklist item specifies the exact claim that constitutes survival (the named value) and the exact claim that constitutes failure (the alternative or a reversal). Do not count additions-that-preserve as rework. |
| **T8** | **Arm-machinery confound on the stress stage — Arm A stress runs INSIDE a panel session, generating structured output that is longer and more visible** | **M** | If stress stage runs through PRISM arm machinery (Arm A = full panel, Arm B = orchestrator-only), the stress session's OUTPUT quality varies by arm. A more thorough Arm A stress session finds more to rework — biasing against Arm A. A weaker Arm C stress misses legitimate rework — inflating Arm C survival. This is a confound on the MEASUREMENT TOOL, not the design quality. | **Same as T1 guard: run all stress sessions under identical vanilla Sonnet with no arm machinery.** The arm machinery is ONLY applied to the design stage. Stress stage is arm-agnostic. This is a necessary corollary of T1's guard, not a separate intervention. |
| **T9** | **Scoring gameability — binary checklist items are written loosely, allowing the scorer (human or script) to resolve ambiguous cases toward preferred outcome** | **M** | If a checklist item says "Was the projection strategy reworked?" a human scorer can resolve ambiguity based on their read of which arm produced better work. Confirmation bias inflates Arm A (panel "should" be better). Script scoring breaks on formatting variance between arms. | **Three-layer hardening:** (1) Each checklist item must reference a specific JSON/markdown field name in the design artifact (e.g., `$.projection_strategy` or `## Projection Strategy` heading text), not a prose description. (2) Script scoring parses that field; human judges only break ties where the field is absent. (3) Items are piloted on one synthetic design before run 1 to confirm the script resolves them deterministically. |
| **T10** | **Panel-firing confirmation gap — Arm A stress sessions are included without confirming `summon_panel=true` fired for THAT session** | **L** | The spec requires exclusion of Arm A sessions where `summon_panel` was not logged. But the harness may tag the commit `arm-A` even if the panel never fired (e.g., classifier downgraded to ROUTINE mid-session). These sessions inflate Arm A's n with orchestrator-only quality, diluting any real panel effect. | **Harness pre-flight: before committing each design session's output, check `prism-routing.jsonl` for `summon_panel=true` with matching session_id. If absent, mark session as EXCLUDED and do not proceed to stress.** The pre-reg already requires this; the guard is making the harness enforce it mechanically, not as a post-hoc audit. |
| **T11** | **Stress-dimension specificity mismatch — some tasks have narrow stress attacks (P4-06: flush within 5s) while others are broad (P4-04: 30-day offline client)** | **L** | Narrow attacks produce high-variance binary outcomes (either the design named CDC or it didn't). Broad attacks allow partial rework that is harder to classify as binary. Variance is unequal across tasks, inflating standard error and reducing power below the n=6 estimate. | **Checklist items for broad-attack tasks (P4-04, P4-01) must be decomposed into sub-items that each target a single named decision point, not the aggregate scenario.** The 80%-pass threshold must be computed over the same item count across all tasks. |

## Executor and Machinery Confound — Extended Analysis

This is addressed as T1 and T8 above, but deserves a consolidated statement.

The pre-reg spec says "6 tasks × 2 stages (design + stress)." It does NOT specify whether the stress stage runs under arm machinery. This silence is the single most dangerous gap in the current design.

**Scenario A — stress runs under arm machinery.**
Arm A design was produced by a panel. Arm A stress is also produced by a panel. The panel may be more thorough in finding rework targets (biasing AGAINST Arm A survival) OR it may be more sympathetic to its own design conventions (biasing FOR Arm A survival). Both effects are plausible; neither can be separated from design quality.

**Scenario B — stress runs vanilla for all arms.**
The measurement tool is identical across arms. Any survival difference is attributable entirely to the design stage, which is the variable we care about. This is the only valid configuration.

**Scenario C — stress runs under a different arm's machinery (e.g., Arm B machinery scores Arm A designs).**
This introduces adversarial noise without controlling it. Worse than A.

**Recommendation:** Scenario B is mandatory. The harness must hard-code the stress executor as `model: sonnet`, no PRISM hooks, `PRISM_PANEL_DISABLED=true` (or equivalent isolation), regardless of which arm produced the design. This must be stated as a fourth non-negotiable before run 1.

## The One Threat Most Likely to Silently Void This Run

**T1 / T8 — the stress executor is not explicitly frozen.**

The pre-reg does not specify what machinery runs the stress session. If the harness defaults to running the stress stage under the same arm configuration as the design stage (the obvious implementation), then Arm A stress is run by a panel, Arm B stress by an orchestrator, and Arm C stress by vanilla. Every survival difference is then confounded by the quality of the measurement tool, not the design quality. The result could show Arm A surviving MORE (panel stress pulls punches) or LESS (panel stress is more aggressive), and there is no post-hoc way to disentangle this from real design quality. The experiment would produce a confident-looking p-value over data that answers a different question: "does a panel STRESS session find fewer flaws in a PANEL design?" not "does a panel DESIGN survive a fixed external stress?" This threat is silent because the numeric output looks valid — commits are tagged, checklist items are binary, Fisher test runs — but the construct validity is void.
