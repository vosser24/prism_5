**Substrate:** a throwaway Django+React "coffee-ledger" project at `Y:\Documents\utilities_projects\prism-stress-test\` (Django 6.0.5 / DRF 3.17.1, 23 tests pass, 29 files) — built purely as a second real project so PRISM has something to act on. **The app is not the deliverable; PRISM is the system under test.** Plus **this session itself**, which did real v5.0 work (claude-master→Opus 4.8, three code reviews, six fixes) under **live v5.0 PRISM** — used as the productivity experiment.

**Method:** PRISM's own instruments (`prism-audit-runner.mjs`, `prism-telemetry-aggregate.mjs`, `prism-bootstrap.mjs`, `prism-recall.mjs --cross-project`) + direct hook invocation with representative payloads + the 623-event live routing log. ## Headline findings (in severity order)

1. **🔴 CRITICAL — a false-positive panel summon can DEADLOCK the session with no in-session escape.** On a *task-notification turn* (no user request at all), the tier router scored `opus, panel=true` on the *"release-screen / release/meta-work"* keyword — matching our **release-saturated conversation context**, not any request. The dispatch-guard then denied all parent Write/Edit/Bash until `@master-orchestrator` was spawned. Worse: **the block cascades to dispatched subagents** (a general worker spawned during the panel turn was itself blocked), and **every documented override is unreachable autonomously** — `!opus-force:` is a user prompt prefix, `PRISM_DISPATCH_GUARD=off` is a pre-session env var, settings edits need the (blocked) Write tool, and the in-band *"write the turn-tier override file as your first action"* is self-defeating because that Write is exactly what the guard blocks (and Write needs a prior Read). The session only recovered on the next user turn (fresh classification). **For a routing system, a routing false-positive that halts all work is the most important pre-publish issue here.**

2. **🟠 Two of PRISM's own self-observability instruments have drifted from the v5.0 schema and actively mislead.** The runtime hooks are correct (245/245 F4 + 30/30 state tests green; router/guards/safety all behave correctly when exercised directly) — but:
   - `/prism-audit-full` (v3.6 catalog) reports **13/29 "fail"**, of which ~11 are stale expectations or Windows harness artifacts (see Axis 2), only 1 a real gap.
   - `prism-telemetry-aggregate` reports `guard_denies=0, classifier_sources=0, panel_summons=0` while the same rollup's `event_kind_counts` shows `mutation_guard:304` and a raw scan finds `summon_panel=true`×12.
   A user trusting either would conclude "PRISM is ~half broken" or "guards never fire." The instruments rotted; the engine didn't.

3. **🟡 The v5.0 LLM re-rank is effectively dormant on Windows.** Across every cross-project query it fell back to BM25 — via the 8s timeout vs ~20s `claude -p` cold-start (confirmed live at 9001ms), tier=`trivial` skipping, and a gate on a *separate* `.prism-kb-index.json` resource index whose absence prints a user-facing `ERROR: ERROR: index missing …` line (doubled prefix; exit still 0).

## Round 5 — §6.B Torture Battery: privacy / security adversarial (highest stakes)

Scope: the cross-project knowledge-index egress surface. Drove `buildKnowledgeIndex()` directly with planted-secret corpora. Harness: 49 assertions + dedicated probes.

### Findings
- **🟠 B2 — keyword-less high-entropy secret leaked into the egress index (FIXED).** `scanSecrets`' 10 keyworded patterns (correctly redact all 10 in B1) do NOT flag a bare high-entropy token — a 64-char hex hash or an API-key-shaped blob with no recognizable prefix. Such a token **survived verbatim as a `postings` term** (and could enter `keywords_top`), reaching the global cross-project index AND the `claude -p` rerank egress. The "descriptor-not-body" defense caps multi-word prose and full lines but NOT a single high-entropy token. **FIXED (defense-in-depth):** `dropHighEntropy()` removes long hex hashes (`^[0-9a-f]{32,}$`) and long mixed-class blobs (≥40 chars w/ both letters+digits) from `postings` + `keywords_top` in all three entry builders (markdown/panel/verdict) — these are never legitimate BM25 search terms, so recall is unaffected (guard test: ordinary words on the same line still indexed). TDD'd in `test-prism-kb-knowledge-indexer.mjs` (59/62→62/62), synced live. ([[feedback-regex-intervening-word-class]] is the routing analogue; this is the privacy analogue — a keyworded matcher missing a valid-but-unkeyworded input.)

### Verified SAFE (no finding)
- **B1 — all 10 SECRET_PATTERNS** (sk-/gho_/AKIA/PEM/key=value/Slack/Google/JWT/Stripe/URL-creds) redact the whole entry (`redacted=true`, `postings={}`, `description=placeholder`); the secret literal never appears anywhere in the index. ✅
- **B3 — default-deny holds** under every variant: no `.prism-kb-share.json` → 0 entries; corrupt marker → 0 (fail-closed); `shared_types:[]` → 0; type-scoped (share only `plan`, withhold `lesson`) → lesson absent. ✅
- **B4 — corpus-walk symlink/junction escape: NOT exploitable.** Empirically tested the strongest unprivileged Windows vector — a **directory junction** (no admin needed) inside `tasks/workspace/`. Node's `Dirent` reports `isDirectory()=false, isSymbolicLink()=true` for it, so `listPanelJson`'s `if (ent.isDirectory())` never recurses into it → foreign content is NOT indexed. POSIX `dir` symlinks hit EPERM here but share the same Dirent (lstat) semantics. `..` traversal isn't injectable (hardcoded corpus dirs; readdir entry names can't contain separators). The Round-scout's flagged "no isSymbolicLink guard" gap is therefore a *theoretical* code-style note, not a live vuln — no code change made (adding untested defensive code would be noise). ✅
- **⚪ Writer/file asymmetry (noted, not a hole):** `writeShareMarker(root, [])` defaults to ALL shareable types (documented helper convenience), whereas a hand-written file with `shared_types:[]` shares nothing. The enforcement gate (`collectProjectEntries`) reads the file's array, so the security boundary is the on-disk array — opt-in only. Footgun for the helper, not an exfil path.

**Round-5 net:** 1 real privacy fix (high-entropy postings/keyword leak), TDD'd; default-deny + all keyworded redaction + corpus-walk-escape verified robust. Full state suite **21/21**, audit **29/29** green post-fix. §6.B closed. Remaining: C lifecycle, D F4-scale, E telemetry, F productivity-A/B.

### Pending decision — index scaling (O(N_total) write-amplification)

### Fix 9 🟠 — §4#4 safety-gate OVER-FIRE (the deferred one from "Fixes applied")
The gate substring-scanned the RAW command, so a dangerous token sitting inside a **quoted argument / JSON data** tripped it — it had blocked two of the campaign's own measurement commands. Root cause is two-fold and both are now fixed in `hooks/prism-safety.mjs`, **TDD'd red→green** (`tests/v3/state/test-prism-safety-overfire.mjs`, **15/15**):
- **De-quote before scanning shell-command dangers.** `rm -rf` / `rm`-path / `mkfs` / `dd` / `curl|bash` are now matched against a de-quoted view, so `git commit -m "stop using rm -rf"`, `echo '{"x":"rm -rf /tmp"}'`, and `grep -r "rm -rf" .` ALLOW. **Anti-under-block guards (the hard part for a safety gate):**
  - An **eval-wrapper** (`bash -c "..."`, `sh -c '...'`, `python -c`, `node -e`, bare `eval`) makes the quoted text *executable*, so when one is present the command is scanned RAW — `bash -c "rm -rf /"` and `python -c "...os.system('rm -rf /')"` STILL block.

- **Tightened the path rule:** dropped `~` from the `rm -f … <path>` class. A non-recursive `rm -f ~/.prism-kb/tmp.json` is routine cleanup (now ALLOWS); recursive home removal (`rm -rf ~/x`) is still caught by the `rm -rf` rule; system paths (`/etc`, `/home`, `..`) still block.

- **⚪ Residual found DURING this fix (honest, accepted).** Committing this very fix set tripped the gate: the commit message *described* the `curl|…|bash` pattern, and a heredoc body is **not** quoted, so the de-quote pass didn't strip it → over-fire.
