### What Phase J actually ships

**`skills/master-orchestrator/SKILL.md` PHASE 1.5 section** gains three new subsections (after the existing Correctness / Optimality / Hidden-risks subsections, replacing the old single-paragraph "Standard of evidence"):

1. **`### Evidence taxonomy`** — six-row table mapping claim class to required evidence (Performance, Security, Correctness, Completeness, Compatibility, External tool / library). Each row names the bar concretely (e.g. Performance → "benchmark numbers with environment + N, OR comparison against a named baseline").
2. **`### Per-claim verdict`** — three verdict tokens (`EVIDENCED / UN-CITED / REJECTED`) deliberately mirroring PHASE 0d's `ACCEPT / REJECT / CONDITIONAL` shape. Includes bounce-ONCE protocol, KNOWN-LIMITATION fallback on second miss, a "Token note" disambiguating `REJECTED` (PHASE 1.5 evidence verdict) from `REJECT` (PHASE 0d challenge response), an "Aggressive rejection" paragraph capturing the Phase J intent, and a factory-upgrade trigger at ≥3 UN-CITED verdicts per specialist (with explicit disambiguation from the pre-existing `### Factory escalation from senior review` 2+-misses threshold — they fire on different failure modes).
3. **`### Standard of evidence — delegation boilerplate`** — a structured block the orchestrator pastes verbatim into `Agent()` prompts so specialists see the bar at delegation time, not just at review time.

**`### Visible output`** gains a mandatory bullet (`Claims rejected as UN-CITED or REJECTED, and the outcome on the second pass...`) plus a closing paragraph requiring the bullet whenever a bounce occurred — so users see which claims were stress-tested at the evidence layer, not just which survived.

**`tests/v3/state/test-master-orchestrator-evidence-rules.mjs`** — new drift-guard test (9 named tests, ~12 inner assertions): 6 positive Phase J structure assertions + 3 D004 §7 negative invariant assertions (Five Unbreakable Rules preserved, PHASE 0d still at "two", no leakage into thin-wrapper agent file).

## Tactical lessons worth memory (candidates)

This session reinforced one durable lesson worth keeping in auto-memory:

- **Drift-guard TDD-red verification must actually run the test before the spec change lands, not just predict the failure.** My initial Phase J Task 1 plan predicted 6 FAILs / 3 oks. Actual was 5 FAILs / 4 oks because case-insensitive regexes (`/known limitation/i`, `/bounce.*ONCE/i`) silently matched pre-existing lowercase prose (`"Known limitations remaining"`, `"bounced back once"`). Code-quality review caught the false positives and forced uppercase token pinning. **Generalize:** when a drift-guard test is meant to enforce uppercase verdict-style tokens introduced by a new prose layer, drop the `i` flag and pin uppercase forms specifically — otherwise the test passes against pre-change state and breaks the TDD-red contract silently.

Other session-specific lessons that DON'T need memory (the codebase carries them):

- The "Claims bounced" vs "Claims rejected" plan-prose-vs-test-regex internal inconsistency — plan-as-spec discipline issue, but specific to this one plan.
- Multi-line bold matching (`**Bounce\n  back ONCE**`) needing `\s+` not `[^\n]` — narrow regex hygiene, captured in the test's inline comment.
- Section-scoped regex slicing (`raw.split(/^### NEXT/m)[0]`) for invariant assertions to avoid future-fragility — captured in the test code.

## Strategic lessons (carry forward to Phase K + future phases)

- **Subagent-driven-development continues to scale well at sub-day phase granularity.** Phase J was 0.3d budget, 3 dispatchable tasks (plus user-driven Task 4), 9 commits, zero 529s. The two-stage review (spec compliance then code-quality) caught real issues every time: the `/i` flag false positives in Task 1, and three substantive issues in Task 2 (factory-trigger threshold conflict, REJECT/REJECTED collision, lowercase "once"). The implementer's self-review caught NONE of these. Continue using subagent-driven for Phase K despite its smaller-than-Phase-D scale — the review loop's catch rate justifies the dispatch cost.

- **Plan-as-spec discipline matters even for 0.3d phases.** Phase J's plan had two internal inconsistencies (regex case-sensitivity vs prose token casing, bullet wording vs test regex) that only surfaced under review. Mitigation for Phase K: write the plan, then *read it like a reviewer* before saving — does Task N's test match Task N+1's prose? Are exit codes consistent? Are heading strings stable across mentions?

- **Final cross-implementation review caught something the per-task reviews missed.** The bounce-ONCE assertion's `[^.\n]` exclusion meant the primary normative bullet (where `Bounce` and `ONCE` wrap across two lines) was never matched by the test — yet that's the bullet a future contributor is most likely to revert. Per-task reviewers looked at one task's code; only the final reviewer had both the test (Task 1) and the prose (Task 2) in scope simultaneously. **Lesson:** always run the final cross-implementation review even for small phases. The two-stage per-task review is necessary but not sufficient.
