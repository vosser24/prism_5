## Renderer kwarg symmetry — when two codepaths share a renderer, audit kwarg pass-through from both callers

**Context.** Phase H Task 7 manual dog-food (in the `competition_agents/` testbed) surfaced a subtle correctness bug: `/prism-deep-dive --upgrade <slug>` would silently bump the `created:` field of the master agent file on every Apply, even though the agent body itself was unchanged. Root cause was a kwarg-passing asymmetry: `diffMasterAgent` extracted the on-disk `created:` date and passed it to `renderMasterAgent({slug, protocol, created})` so the diff would not show calendar drift (commit `9cb56ed`), but the sibling `writeMasterAgent` codepath called `renderMasterAgent({slug, protocol})` *without* the `created` arg — so when `agent-write --force` ran, today's date won and the field got rewritten.

**The general lesson.** When two (or more) codepaths share a common renderer function, *every kwarg the renderer accepts must be passed consistently from all callers*. Even if one caller doesn't seem to need a particular kwarg, omitting it means that caller silently diverges from the others. The asymmetry is invisible at the call site (the function still works) and only manifests downstream — here, as "Apply broke the invariant that an immediate diff after Apply should be empty."

**Concrete heuristic for code review.** When you see a change that adds a kwarg to a shared renderer:

1. `git grep '<renderer-name>(' -- '*.mjs' '*.js' '*.ts'` to enumerate every caller.
2. For each caller, ask: *should this caller pass the new kwarg too?* If yes, pass it. If no, write a one-line comment explaining why this caller deliberately omits it.
3. If the kwarg has a sensible default that makes "not passed" equivalent to "default", document that explicitly in the renderer's signature/docstring — otherwise asymmetric callers will look correct but produce subtly different output.

**How this would have caught the bug at review time.** When commit `9cb56ed` added the `created` kwarg to `renderMasterAgent`, a grep would have surfaced two callers: `diffMasterAgent` (the one that prompted the change) and `writeMasterAgent` (the one that needed the same treatment but didn't get it). The reviewer would have asked "should writeMasterAgent also pass `created` on the force-overwrite path?" and the answer is obviously yes — that's exactly the symmetry the dog-food test eventually surfaced.

**Where this applies in PRISM.** Anywhere two slash commands wrap the same helper function but with different goals (e.g., `agent-diff` reads + compares, `agent-write` reads + writes; `next-d-number` reads, `append-decision` reads + appends). Any shared helper that accepts state-extraction kwargs is a candidate.

**Fix landed.** Commit `e98da31`. Five-line change in `tools/prism-deep-dive.mjs:222-238` mirroring the on-disk read from `diffMasterAgent` into `writeMasterAgent` when `--force` is overwriting an existing file. Regression test in `tests/v3/state/test-prism-deep-dive.mjs:165-196` seeds `created: 2020-01-01` and asserts the date survives force-overwrite — a date far enough in the past that "today" can never coincidentally match.
