## 7. TASK 3 — real-usage stress-test project ("push PRISM to the limits")
**Goal (user's words):** a full testing setup **in a NEW test-folder project** (separate from this repo) that pushes PRISM to its limits and measures **performance, compliance, productivity, and results against what PRISM was designed to do.** This is real-usage acceptance testing of PRISM-as-a-product, not more unit tests of the repo.

**Why a separate project:** PRISM installs globally into `~/.claude` and acts on whatever project you're in. To measure it honestly you need a clean, representative target project (its own git repo, its own `docs/prism/`, its own CLAUDE.md) that you drive through realistic workflows — NOT the PRISM source repo (which is self-referential and skews routing/guards).

**Starting point — reuse what exists, then go beyond:**
- `/prism-audit-full` + `tools/prism-audit-runner.mjs` already exercise every hook code path via synthetic scenarios and emit a timing/coverage/trigger-correlation matrix. **Run it first** as the baseline instrument; the new project EXTENDS it with real-usage + the 4 measurement axes below.
- `/prism-health`, `/prism-telemetry` (rollup at `~/.claude/.prism-telemetry-rollup.json`: cost, classifier accuracy, guard fire rate, tier distribution) are the built-in metric sources — wire them into the report.

**Scaffold (suggested):** `Y:\Documents\utilities_projects\prism-stress-test\` — a small but non-trivial multi-file app (mixed languages / a few subsystems) so tier classification, dispatch, recall, and the F4 cross-project index have real material. Run `/prism-bootstrap` in it, then drive scripted scenarios.

**The four measurement axes (define a metric + pass-bar for each):**
1. **Performance** — per-hook latency (SessionStart sweep, UserPromptSubmit router/classifier, PreToolUse guards), end-to-end added latency per turn, `/prism-recall` (3-tier) latency, `--cross-project` BM25 vs re-rank (remember the ~20 s Windows `claude -p` cold-start), index build time at scale. Push it: large corpus (hundreds of lessons/adjudications), many files, deep dirs. Bar: hook overhead within a stated budget; no pathological walks.
2. **Compliance (does it do what it's designed to do?)** — measure against the design intent in `docs/prism/adjudications/` (esp. D004 product vision), `README` value prop, and the F4 design (`../plans/2026-05-29-F4-design.md`). Check: tier-routing accuracy on a labeled prompt set; guards fire when they should and *don't* over-fire (the release-screen fix is the canonical example — verify readiness questions no longer summon panels); privacy invariants (default-deny sharing, descriptor-not-body, no-network, no API key); adversarial-review actually produces ≥2 substantive challenges. Bar: documented behaviors hold; classifier false-positive/negative rate within target.
3. **Productivity** — does PRISM net *help* or add friction? Run representative tasks (a feature, a bugfix, a refactor, a planning task) with PRISM vs a control (PRISM guards off / vanilla CC) and compare: turns-to-done, total cost (telemetry), rework, friction events (spurious guard blocks, forced panels). Bar: net-positive on cost-discipline without a productivity tax that outweighs it.
4. **Results vs design intent** — the headline bets: does cost-disciplined tier routing actually save money (telemetry cost/tier distribution)? Does the F4 cross-project index surface genuinely-relevant prior knowledge across ≥2 projects? Does the adversarial panel catch real issues a single pass misses? Score each bet delivered / partial / not-yet against its design promise.

**Deliverable:** a structured report (markdown) under the stress-test project (and/or `docs/prism/` here) with the matrix of axis × metric × measured-value × pass-bar × verdict, plus a prioritized findings list feeding TASK 4 (triage + fix). Capture durable lessons via `/prism-clean`.

**Scope discipline:** this can balloon — timebox it, log any axis left only partially measured ([[feedback-top-class-quality-bar]] wants honest scoping over false coverage). It does NOT block delivery if it surfaces only non-blocking findings; blockers feed TASK 4 before the §5 merge.
