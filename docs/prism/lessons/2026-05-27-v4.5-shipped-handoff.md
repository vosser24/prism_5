## Known v4.5 limitations carried into v4.6

### Critical-class (none — caught and fixed during reviews this session)
All Critical-class findings from per-phase + cross-phase reviewers were resolved before merge. The reviewer pattern (per-phase + cross-phase) worked as designed; without it, three separate Critical bugs would have shipped (Phase 1+2 manifest gaps, Path B dead code, LITE reviewer orphan).

### Telemetry-shape limitations (acknowledged in CHANGELOG)

1. **`dispatch_cap` events emit `{cap, subagent_type, description}` only** — spec also listed `actual_parallel` and `queue_depth`, but Claude Code's `PostToolUse[Agent]` event doesn't expose sibling-dispatch state. v4.6 calibration must either compute siblings from on-disk task-dir state, or accept the narrower signal.

2. **`phase_0d_challenge` events emit `evidence_class: 'UNCLASSIFIED'`** — Layer 4 panel-guard doesn't pre-classify `panel.positions[].challenges[]`. v4.6 will need to derive evidence-class downstream from challenge text, OR extend panel-guard to compute and write the field at panel-write time.

### Locking limitations

3. **`withRosterLock()` wraps 3 of ~6 mutation sites.** Wrapped: `prism-roster.mjs`, `prism-phase-1-5-oob.mjs`, `prism-phase-0d-oob.mjs`. NOT wrapped: `prism-agent-write-register.mjs`, `prism-uninstall-cleanup.mjs`, `prism-installer.mjs`. Concurrent writes from those sites against the locked sites can lose updates under contention. v4.6 should extend the lock or document the race window per-site.

### Cosmetic / deferred from v4.5 plan

4. **`tools/lib/prism-verdict-flag.mjs` is hardcoded to `.prism-phase-1-5-*` paths.** The phase-0d hook inlines its own `atomicWrite` instead of using the lib. Refactor to accept a `kind` parameter and unify both hooks → deferred to v4.6. ~0.5d work.

5. **Windows `claude` resolution.** `spawnSync('claude', ['-p', ...])` without `shell: true` does not resolve `.cmd` files. Affects both `prism-phase-1-5-oob.mjs` and `prism-phase-0d-oob.mjs`. Plan T38 step 4 (behavioral smoke) would surface this if it's a real production issue on Windows installs; if so, a `fix(prism): v4.5 post-tag — Windows .cmd resolution` commit + v4.5.1 patch tag is the right move.

6. **SCOPE GUARD heuristic is intentionally loose** (keyword overlap on 4+ char tokens). Real adversarial panels often use vocabulary not in the scope phrase, so this is advisory-by-default with `PRISM_SCOPE_GUARD=strict` opt-in. v4.6 may upgrade to a stronger heuristic (TF-IDF, character trigrams, or LLM-based judgment).

## Strategic lessons captured this session

These either confirm existing memories or are candidates for new ones:

1. **`[[feedback-cross-phase-review-pattern]]` paid for itself again.** Per-phase reviewers caught real bugs in Phases 3 and 4, but the cross-phase reviewer at T35 caught 3 MORE Critical/Major issues that ONLY became visible across layer boundaries: a Layer 2 LITE prompt file orphaned because Layer 3's manifest didn't include it; a CHANGELOG claim from Phase 5 that contradicted Phase 2 reality. Per-phase reviewers see their own commits; cross-phase reviewer sees the whole branch. Both are necessary.

2. **`[[feedback-subagent-test-count-decay]]` confirmed again.** A Phase 3 implementer reported a bootstrap test failure that was a phantom (re-run cleanly 34/34). An F8 installer test reported 1 failure in one sweep; 3 follow-up runs all 87/87. Subagent test-count claims must always be ground-truthed by the controller running the suite directly.

3. **`[[feedback-pace-per-task-vs-phase-review]]`** (existing) **strongly confirmed.** Per-task implementer dispatch + phase-level review is right for PRISM's 7-15 small-task phases. Per-task review would have added ~30 subagent invocations to this session for the same correctness — the per-phase + cross-phase combination caught everything.

4. **Plan code-blocks have small drift risks** (existing carryover from Phase 1+2 handoff). Confirmed AGAIN in Phase 3 (T24 plan template called `parseTargetFlag` + `detectInstallation` + `backupInstallation` — none of those names existed; implementer correctly adapted). The "directionally correct, locally adaptive" plan pattern works because implementers handle these via DONE_WITH_CONCERNS, and the controller does the route-to-real-helpers translation upfront in the dispatch prompt.

5. **(Candidate new memory)** **`[[feedback-installer-manifest-coverage-cross-check]]`** — When a phase adds new files to the repo, the SAME phase must add them to `tools/install-manifest.json` `files[]` AND `remove_on_upgrade_patterns`. The cross-phase reviewer catches omissions, but a sweep test in `test-plugin-manifest-drift.mjs` (or a new `test-installer-coverage.mjs`) would catch this earlier: assert every `hooks/prism-*.mjs`, `tools/prism-*.mjs`, `agents/*-reviewer.md`, etc., in the repo is in manifest.files[]. Worth adding in v4.6.

6. **(Candidate new memory)** **`[[feedback-windows-gh-cli-absent]]`** — On this dev box, `gh` is not installed (no scoop, no Programs/gh, no WinGet GitHub.cli). v4.6 plans that include "open PR via gh" should either include gh installation as a prereq step OR provide the manual web-URL fallback (`https://github.com/<user>/<repo>/pull/new/<branch>`). The latter is already universal-correct.
