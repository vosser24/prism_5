## Notable design calls + reviewer-flagged issues addressed

- **`skills: [master-orchestrator]` unconditional in master-<slug>.md frontmatter** (D004 §3 locks this). Pre-Phase-E the skill doesn't exist; Claude Code's missing-skill behavior is unverified (silent no-op vs error). Smoke-test concern for Task 11.
- **Pre-staged unused imports** (Task 1 → Task 6): plan-approved pattern, avoids edit-churn. Validated by Task 1 reviewer.
- **Atomic write divergence**: `writeMasterAgent`/`writeMemoryMd`/`writeSettingsAgent` use the simple `path + '.tmp'` + `renameSync` pattern matching `prism-agent-write-register.mjs`. Only `writeStateAtomic` uses the robust pid-random + cleanup pattern. Project convention: state files robust, content files simple.
- **stdout format split**: `slug-derive` outputs JSON (machine-parsed); write subcommands output plain `wrote <path>` (human-readable). Forward-compat OK because the slash command checks exit codes, not output text.
- **Two state writes per phase-project-master invocation** (markPhaseStarted then markPhaseCompleted) — spec-faithful; gives crash-resume visibility if slug-derive subprocess hangs.
- **Bootstrap helper cannot AskUserQuestion** by design. When slug-derive needs prompting (generic basename + no CLAUDE.md identity), the helper bails to "run /prism-deep-dive" rather than completing the phase. Task 11's smoke didn't exercise this path because `competition_agents` is a non-generic basename.

## Tactical lessons (worth keeping)

- **Windows `spawnSync` hits `ENAMETOOLONG` (~32 KB OS arg-length limit)** when CLI tests pass inline JSON >32 KB. Task 4's 25 KB cap test was inflated to ~68 KB JSON; on Windows it returned `status: null` before the helper ran. **Fix pattern**: any test fixture larger than a few KB should `writeFileSync` to a tempfile and pass the path via `--<arg>` instead of inlining. Apply to all future Node CLI tests on Windows.

- **`new URL(..., import.meta.url).pathname` returns `/Y:/...` on Windows**, which `spawnSync` mis-resolves to `Y:\Y:\...` (the `Y:` interpreted as volume + the leading `/Y:` prepended as directory). **Fix**: use `fileURLToPath(new URL(...))` from `node:url` for any sibling-module path resolution that gets passed to `spawnSync`. Caught in Task 9; document as a Windows portability rule.

- **The "strip checksum via destructure" idiom in state mutators leaves `checksum: undefined`**, which the `writeStateAtomic` validator rejects BEFORE the recompute step. The validator pre-checks `state.checksum !== null && typeof state.checksum !== 'string'` → undefined fails. **Fix pattern**: mutators that touch state should `return {...state, [field]: value, checksum: null}` (explicit null) rather than destructuring `checksum` away. Task 6's `setProjectSlug` had this bug; Task 9 worked around it; Task 9's fix corrected the root cause. Lesson applies to any future state mutator that wants to invalidate the checksum.

- **Verbatim plan paste + small inline fixes is the right granularity for subagent-driven dev**. The 11-task plan averaged ~1 implementer dispatch + 1-2 reviewer dispatches per task. Reviewer feedback led to follow-up commits on 4 of 11 tasks (Task 2, Task 4, Task 5, Task 9) — each fix was <60 lines and addressed a single specific issue. The two-stage review (spec then quality) reliably caught real issues without forcing implementers into a redesign loop.

- **Reviewer "Approved with notes" verdicts that conflict with plan locks should be evaluated, not auto-applied**. Task 3's reviewer pushed back on `skills: [master-orchestrator]` being unconditional; D004 §3 explicitly locks this. Accepted reviewer's note as forward-compat info, declined to deviate from plan. Same pattern: pre-staged imports (Task 1 review re-litigated in Task 2; Task 1's decision held).

## Strategic lessons (for v4.0 remaining phases)

- **Subagent-driven development scaled well at 11 tasks / 14 commits / 132 tests over one session**. Zero 529s this session (vs ~40min lost to 529s in the v3.11.0 session per prior handoff). Anthropic API stability may have improved, OR the smaller per-task scope (vs Task 2 of v3.11.0 which dispatched 6 subagents in a row) reduced collision pressure. **Recommendation**: keep subagent-driven as the default for v4.0 Phase E/F/H/J/K; tasks are smaller still, so the cost-benefit only improves.

- **The /prism-clean dog-food found a real classifier UX miss**: user intuition treats "explicit Locked design decisions" as L5; spec reserves L5 strictly for panel adjudications. **Fix candidate for D002 §6 update** (or v4.1): add L5 trigger row for "user-stated `Locked` decision that changes a codebase-wide convention, no panel required." Recorded in the prior session's dog-food report (see [[2026-05-25-session-handoff]]).

- **The deterministic-surface / LLM-judged-surface split is load-bearing**. Every Phase D piece had a clean line: `tools/prism-deep-dive.mjs` is 100% deterministic (slug, write, validate); `commands/prism-deep-dive.md` is 100% LLM-judged (discovery synthesis, AskUserQuestion, deviation handling). This split made the testing trivial (subprocess + mkdtemp covers all the deterministic logic) and the slash command auditable (the prose IS the spec). **Pattern to apply to Phase D-onwards**: every new feature gets one helper.mjs + one .md, never inlined.

- **D004 Phase E should start with a smoke gate**. Before migrating master-orchestrator agent → skill, verify Claude Code's behavior on a master-<slug>.md whose frontmatter says `skills: [master-orchestrator]` BUT the skill doesn't exist. Three possibilities: (a) silent no-op (best — Phase D current state is fine); (b) startup error (bad — pre-Phase-E master agents are broken); (c) loader warning (manageable). The smoke test for Phase D Task 11 will surface this incidentally.
