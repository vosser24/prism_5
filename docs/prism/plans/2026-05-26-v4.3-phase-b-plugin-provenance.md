# v4.3 Phase B — plugin-vs-manual provenance + `/prism-uninstall-cleanup`

## Goal (one sentence)

When the agent-factory creates a new agent while PRISM is running as a plugin (`$CLAUDE_PLUGIN_ROOT` set), the roster entry is tagged `installed_via: "plugin"` so the user can clean those agents up via `/prism-uninstall-cleanup` before `/plugin remove prism` — without losing manually-created agents.

## Non-goals

- **Not** switching the agent write target on `$CLAUDE_PLUGIN_ROOT` (the handoff predicted this; it was wrong). Agent files always live at `~/.claude/agents/<name>/` and `~/.claude/agents/<name>.md`.
- **Not** wiring a SessionStart "we used to be a plugin" detection fallback. Single explicit slash command is the only trigger.
- **Not** refactoring all factory write paths into a JS helper. Provenance is set via prose instructions to the agent + a deterministic test guard.
- **Not** touching `--master-<slug>` mode (writes to project-local `.claude/agents/`; provenance doesn't apply there — explicit exception in the prose).

## Design (1) — provenance field

One new field on each roster entry:

```json
{
  "name": "nuclear-physicist",
  "source": "agent-factory",
  "installed_via": "plugin",
  "...": "..."
}
```

Semantics:

| Value | Meaning |
|---|---|
| `"plugin"` | Created while `$CLAUDE_PLUGIN_ROOT` was set in the factory's environment. Eligible for `/prism-uninstall-cleanup`. |
| `"manual"` | Created while `$CLAUDE_PLUGIN_ROOT` was unset (user ran PRISM via `install.sh` or by cloning). **Never** removed by cleanup. |
| missing | Treated as `"manual"`. Safe default for legacy entries — no data loss. |

The `source` field (existing: `"agent-factory"`, `"from-notebook"`, `"reconcile"`) is **orthogonal**. `installed_via` is a separate axis.

## Design (2) — slash command

`commands/prism-uninstall-cleanup.md` is a thin wrapper invoking `tools/prism-uninstall-cleanup.mjs`.

Behavior:

1. Read `~/.claude/skills/prism-plan/references/roster.json`.
2. Filter `roster.agents` to entries where `installed_via === "plugin"`.
3. If empty → `Nothing to clean up — no plugin-created agents found.` exit 0.
4. Else print the list with creation date + a 3-option prompt:
   ```
   How would you like to clean these up?
     [a] Remove all
     [s] Select per-agent
     [k] Keep all (cancel)
   ```
5. For each selected agent: `rm -rf ~/.claude/agents/<name>/`, `rm ~/.claude/agents/<name>.md`, and delete the roster entry. Write roster atomically (temp file + rename).
6. Report: `Removed N agents. Run /plugin remove prism to finish uninstall.`

Flags:
- `--dry-run` — list what would be removed, perform no writes
- `--mode=remove-all` — non-interactive, removes everything tagged `"plugin"`
- `--mode=keep-all` — non-interactive, exit 0 without changes (mostly for tests)

## Design (3) — where the env-var check happens

`agents/agent-factory.md` is a prose-driven Claude Code agent. The check is added to its prose, not to a helper script.

Three sections touched in `agent-factory.md`:

1. **`## CREATE PROTOCOL` step 4** ("ALWAYS update GLOBAL roster") — append `installed_via` to the required fields list, with explicit Bash example: `installed_via: "$([ -n \"$CLAUDE_PLUGIN_ROOT\" ] && echo plugin || echo manual)"`.
2. **`## Mode: --from-notebook` step 5** — same addition to the roster registration.
3. **`## Mode: --master-<slug>`** — explicit one-line note: "`installed_via` does NOT apply to master agents (they live in project-local `.claude/agents/`, not under `~/.claude/agents/`). Skip this field for master entries."

Test guard: `tests/v3/state/test-prism-uninstall-cleanup.mjs` includes a smoke that spawns a tiny node script with `CLAUDE_PLUGIN_ROOT` set vs unset to verify the env-detection logic returns the expected value. The test does NOT exercise the markdown agent itself (that's a Claude Code prose surface), but it pins the contract.

## Design (4) — test surface

New file `tests/v3/state/test-prism-uninstall-cleanup.mjs`, 6 cases:

1. **backfill-safety**: roster with three entries all lacking `installed_via` → cleanup tool's `--dry-run` lists zero.
2. **plugin-only-filter**: roster with one `"plugin"` + two `"manual"` → `--dry-run` lists exactly the plugin one.
3. **zero-state-idempotent**: empty `roster.agents` → exit 0 + stdout "Nothing to clean up".
4. **removal-correctness**: in a tempdir mocked as `$HOME/.claude/`, with one `"plugin"` agent + directory + flat file + one `"manual"` agent + directory + flat file → after `--mode=remove-all`: plugin agent's directory + flat file + roster entry are gone; manual agent untouched on all three.
5. **roster-write-atomic**: kill the process mid-write (SIGTERM after roster.tmp creation but before rename) → roster.json on disk is still the pre-state. (Use a `PRISM_TEST_PAUSE_MS=…` injection point.)
6. **env-detection-smoke**: spawn `node -e "console.log(process.env.CLAUDE_PLUGIN_ROOT ? 'plugin' : 'manual')"` with env set vs unset; assert outputs.

Plus update `tests/v3/state/test-plugin-manifest-drift.mjs` only if `plugin.json` grows a `commands` block (currently doesn't list slash commands — verify and decide).

Target: +6 tests → 106 → 112 across 8 suites (7 existing + new uninstall-cleanup).

## Open risks

1. **Roster schema drift** — if some other slash command writes roster without `installed_via`, those entries silently become "manual" on next read. That's actually the desired backfill behavior, but worth a reconciler test on `/prism-index` later.
2. **`/prism-uninstall-cleanup` after partial uninstall** — if user removes plugin first, then tries to run the slash command, the command is no longer registered. MIGRATION doc must emphasize "BEFORE /plugin remove".
3. **Roster path resolution** — if `roster.json` lives at a non-default path (some users symlink), the tool needs to resolve it via the same logic as the existing reconciler. Reuse, don't reimplement.

## Out of scope (defer to Phase C or later)

- SessionStart fallback detection of "plugin used to be here"
- Multi-plugin uninstall coordination
- macOS-native verification (separate test plan)
- Migration of legacy `~/.claude/agents/` manual entries to "plugin" if user later upgrades to plugin install (not a real workflow)
