# v4.4 design — OOB PHASE 1.5 reviewer + skill refactor + telemetry

**Status:** Draft

**Captured by:** /superpowers:brainstorming session
**Related:** [[D004-v4-product-vision]] [[D007-agent-creator-vs-factory]] [[2026-05-26-v4.3-phase-b-shipped]] [[2026-05-26-v4-line-landed-on-main]] [[feedback-handoff-backlog-reverify]] [[feedback-drift-guard-tdd-red-verification.md]]

## One-sentence summary

v4.4 ships an out-of-band PHASE 1.5 reviewer (independent from the master, invoked via SubagentStop hook + headless Anthropic SDK call), refactors the 770-line master-orchestrator skill into 11 focused references for compaction-survival, and adds telemetry-pair instrumentation on verdicts plus a lite Phase 1.5 variant for FULL-ROUTINE tasks — closing 14 of 32 evaluation-flow gaps identified during the gap-analysis brainstorm. The remaining 18 gaps become the v4.5/v5.0 backlog, prioritized by telemetry data once v4.4 has been in use for 30+ days.

## Motivation

A deep-dive on PRISM's master-<slug> → specialist dispatch surface surfaced 32 distinct gaps clustered into 7 families: bias/independence, measurement/telemetry, structured-output, coverage holes, stale/drift, cross-phase coupling, and refactor hygiene. The previous gap-analyses (this session, earlier turns) anchored on "independent reviewer for PHASE 1.5" but were architecturally naive — they didn't ground the proposal in the verified two-level topology constraint (`master-<slug>` as main thread; specialists as Level-2 subagents; subagents-cannot-spawn-subagents is enforced by Claude Code, per `https://code.claude.com/docs/en/sub-agents`).

This spec respects the topology, ships an OOB reviewer that lives OUTSIDE the master's dispatch tree (separate session via headless Anthropic SDK invocation from a hook), and addresses the four immediate ripple effects (workshop tagging, execution timing rule, Phase 0d→1.5 cross-link, roster ratchet integration) plus the compaction-survival refactor surfaced by the same audit.

The work composes: each layer's value depends on the others. C1 alone is half-policy without telemetry; the refactor alone doesn't close any gap but enables future work; lite-1.5 alone leaves the FULL-NOVEL surface unchanged. Bundling all three is the right grain for a v4.4 minor release.

## Architecture

### Three layers, one ship

```
Layer A — Refactor (~1.5d)
  skills/master-orchestrator/SKILL.md (770 lines → 120 lines navigation index)
  + references/ (10 focused files)

Layer B — OOB reviewer + companions (~3d)
  hooks/prism-phase-1-5-oob.mjs           — SubagentStop matcher
  hooks/lib/prism-verdict-flag.mjs        — verdict flag-file lifecycle
  agents/phase-1-5-oob-reviewer.md        — slim reviewer system prompt
  tools/prism-phase-1-5-verdicts.mjs      — verdict log reader/aggregator
  roster.json schema additions            — requires_phase_1_5, requires_phase_1_5_block
  ~/.claude/.prism-task-<id>/panel.json   — 0d→1.5 challenge cross-link
  claude-master.md PRISM-composition refresh (closes G4)

Layer C — Telemetry + lite-1.5 (~2.5d)
  .prism-routing.jsonl schema additions   — phase_1_5 object
  tools/prism-telemetry-aggregate.mjs ext — agreement-rate surface
  references/phase-1-5-senior-review.md   — LITE variant
  tools/prism-roster.mjs --apply-ratchet  — atomic ratchet writer
  3 new behavior tests
```

### Dispatch topology (post-v4.4)

```
master-<slug>  ← Level 1, MAIN THREAD (session agent)
  │
  │  Phase 0: PROPOSAL (panel.json written at end of 0d)
  │  Phase 1: EXECUTION
  │
  ├─ Agent(@specialist) ──→  Level 2 subagent, leaf, STOPS
  │                              │
  │                              ▼  SubagentStop event
  │                       hook: prism-phase-1-5-oob.mjs
  │                       (async, runs OUTSIDE dispatch tree)
  │                              │
  │                              ▼  if roster.<spec>.requires_phase_1_5: true
  │                              │  Anthropic SDK direct call → sonnet reviewer
  │                              │  (no claude -p cold-start; ~$0.01-0.03/review)
  │                              │
  │                              ▼  writes verdict result + appends log
  │
  └─ master proceeds (or block-mode pauses for asyncRewake)

  SessionStart (next turn / next session):
    pickup hook reads pending verdict files
    severity-filtered emission (all-EVIDENCED silent; UN-CITED/REJECTED surfaced)
    additionalContext → master integrates retroactively
```

### Key design choices (with adversarial-pass updates baked in)

| Choice | Decision | Rationale |
|---|---|---|
| Where reviewer lives | Outside dispatch tree (separate process from hook) | Closes ~5 of 6 bias dimensions; respects two-level topology |
| Invocation mechanism | Direct Anthropic SDK call (NOT `claude -p`) | Faster (~5s saved on cold-start), cheaper ($0.01-0.03 vs $0.05-0.15), no prompt-cache pollution |
| Synchronization | Async by default + block-mode opt-in per agent | Default avoids latency tax; block-mode for irreversible-next-step cases |
| Verdict pickup | SessionStart hook + asyncRewake (block-mode) | Reuses existing flag-file pickup pattern; no new infrastructure |
| Severity filtering | All-EVIDENCED silent; UN-CITED/REJECTED surfaced | Reduces noise; preserves attention |
| Task workspace location | `~/.claude/.prism-task-<id>/` (NOT `tasks/workspace/`) | cwd-independent; works for standalone `@master-orchestrator` |
| SHA computation | `sha256(session_id + timestamp_ms + specialist_name + brief_first_100)` | Guarantees per-dispatch uniqueness even on repeat dispatches |
| Phase 0d challenge anchoring | Per-position (NOT per-specialist) | Positions can map to multiple specialists; specialists to multiple positions |
| Kill switches | Per-install + per-specialist + per-session | Defense in depth |

## Data flow

### 4 file formats

**Pending file** (`~/.claude/.prism-phase-1-5-pending-<sha>.json`) — short-lived:

```jsonc
{
  "schema_version": 1, "sha": "...", "session_id": "...", "specialist_name": "@claude-master",
  "task_brief": "...", "specialist_output": "...",
  "phase_0d_challenges": [{"id":"ch-1","challenge_text":"...","expert_response":"ACCEPT","verdict":"SURVIVES (revised)"}],
  "extracted_claims": [{"id":"claim-1","claim_text":"X is fast","claim_class_hint":"performance","source_line":42}],
  "block_master": false, "created_at": "..."
}
```

**Verdict result file** (`~/.claude/.prism-phase-1-5-verdicts-<sha>.json`):

```jsonc
{
  "schema_version": 1, "sha": "...", "specialist_name": "@claude-master", "reviewer_model": "claude-sonnet-4-6",
  "verdicts": [{"claim_id":"claim-1","class":"performance","verdict":"UN-CITED",
                "taxonomy_row":"Performance","evidence_required":"...","reasoning":"..."}],
  "challenges_addressed": [{"phase_0d_id":"ch-1","addressed":true,"evidence":"..."}],
  "summary": {"total":5,"evidenced":3,"un_cited":2,"rejected":0},
  "reviewer_latency_ms": 12450, "completed_at": "..."
}
```

**Append-only verdict log** (`~/.claude/.prism-phase-1-5-verdicts.jsonl`):
```jsonl
{"sha":"abc","session_id":"s1","specialist_name":"@claude-master","summary":{...},"completed_at":"..."}
```

**Routing log extension** (`.prism-routing.jsonl`) — adds `phase_1_5` object per dispatch with verdict_pre/post + agreement_rate.

### Panel.json (Phase 0d → 1.5 cross-link)

Master writes `~/.claude/.prism-task-<task-id>/panel.json` at end of Phase 0d:

```jsonc
{
  "task_id": "...",
  "positions": [
    {"position_id":"pos-1","expert_name":"Claude Code product expert","specialist":"@claude-master",
     "challenges":[{"id":"ch-1","text":"...","response":"ACCEPT","verdict":"SURVIVES (revised)"}]}
  ]
}
```

Hook reads panel.json at SubagentStop, finds positions for the just-stopped specialist, embeds matched challenges in pending file. If no panel.json (standalone session, no 0d), pending file gets `phase_0d_challenges: []`.

### Flow summary

**Async (default):** SubagentStop → hook writes pending → SDK call in background → verdict written → SessionStart pickup on next turn surfaces UN-CITED/REJECTED items with `[Prior turn]` prefix.

**Block-mode** (`requires_phase_1_5_block: true`): hook returns asyncRewake; master pauses; SDK call completes; asyncRewake wakes master with verdicts as additionalContext; master integrates synchronously before next step.

**Telemetry roll-up:** `prism-roster.mjs --apply-ratchet` reads verdict log, applies escalate/deescalate/reset rules to roster.json. Triggered automatically by `/prism-clean` as part of end-of-session hygiene; manually invokable via CLI for testing or recovery. `prism-telemetry-aggregate.mjs --phase-1-5-agreement` reports reviewer↔master agreement rate as v4.5 calibration signal.

## Error handling

Five engineering principles enforced across 24 documented error states (6 categories):

1. **Hook never blocks master on its own errors.** Exit 0 silent + telemetry log.
2. **Verdict integration is master's responsibility.** Drift guards catch mis-integration at CI.
3. **Atomic writes always.** Tempfile + rename. Append-only JSONL.
4. **Severity-filtered visibility.** All-EVIDENCED silent; UN-CITED/REJECTED surfaced.
5. **Kill-switch at every layer.** Per-install (settings.json), per-specialist (roster flag), per-session (env var).

Six failure categories enumerated (24 specific states):
- Hook-side failures (6 states): transcript missing, roster unparseable, pending write fail, SDK 5xx/429/529, malformed JSON, hook crash
- Reviewer-side failures (4 states): rubber-stamp, false-positive UN-CITED, hallucinated claim, timeout
- Master-side failures (4 states): ignore UN-CITED, missing bounce-2 visible output, block timeout, malformed panel.json
- Ratchet/roster failures (4 states): parallel race, corruption, missing-agent ratchet, model upgrade for tool-restricted agent
- Storage failures (4 states): log corruption, task-dir orphans, pending file accumulation, disk full
- Configuration failures (4 states): kill-switch set, API key missing, hook unregistered, legacy roster

Two open decisions:
- **Q1 (529 retry policy):** single retry + 5s backoff (lighter than [[feedback-subagent-529-fallback]] because OOB is async + non-critical)
- **Q2 (bounce-2 KNOWN LIMITATION authoring):** master writes; reviewer issues verdict only

## Open questions

Three genuinely open from the design pass — must be resolved during implementation:

1. **Should master overrides of reviewer verdicts require explicit user confirmation?** Today the protocol says master can override (drift-guard ensures visible-output shows the disagreement). Considered tighter rule (user must confirm override) but deferred — too disruptive to flow. **Decision: defer to telemetry signal in v4.5.** If users frequently disagree with master's overrides, add the confirmation gate in v4.5.

2. **Should panel.json schema include the panel-composition rationale (why these experts, not others)?** Useful for closing G2 (alternatives-considered logging), but expands scope. **Decision: defer to v4.5.** v4.4 panel.json only carries challenges + positions; rationale is a v4.5 extension.

3. **`async` vs `sync` hook semantics at `SubagentStop` — exact behavior is environment-dependent.** Claude Code's hook reference (`https://code.claude.com/docs/en/hooks`) lists `SubagentStop` under the Subagent category but does NOT explicitly list it in either "Blocking via exit 2" or "Cannot block" categories. The v4.4 design assumes:
   - Async mode (default): hook config `async: true`; hook exits 0 quickly; SDK call runs in spawned background process; verdict picked up via SessionStart on next turn.
   - Block mode (`requires_phase_1_5_block: true`): hook runs SDK call inline (within 60s default hook timeout) and exits 0 with verdicts in `hookSpecificOutput.additionalContext`.
   
   **Action item for implementation:** verify exact semantics via small Claude Code test BEFORE writing the hook. If `SubagentStop` exit 2 does NOT block, redesign block-mode to use a different event (e.g., a `Stop`-event matcher post-validation). If `additionalContext` from `SubagentStop` is NOT delivered to master synchronously, redesign to use the `asyncRewake` + flag-file pickup pattern even for "block mode" (in which case "block mode" becomes "fast-pickup mode" — verdicts arrive at next-step start, not before).
