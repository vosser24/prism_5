# v5.0 roadmap — the next major: from self-aware orchestration to self-improving orchestration

**Status:** Roadmap / vision (NOT an implementation plan — each bet below needs its own `/superpowers:brainstorming` → design spec → task plan before any code)
**Date:** 2026-05-28
**Captured by:** v4.5 ship session, forward-planning at user request
**Related:** [[2026-05-28-v4.6-design]] [[2026-05-27-v4.5-shipped-handoff]] [[2026-05-27-v4.4-installer-pending-v5-handoff]] [[feedback-cross-phase-review-pattern]] [[feedback-installer-architecture-pattern]]

## Why this is a MAJOR, not another minor

v4.x has been **additive, backward-compatible polish** on a fixed architecture: classify prompts, route to a model tier, dispatch specialists through the master, review their output out-of-band. Every v4.x item slotted into that topology without changing it.

v5.0 changes the topology and adds a persistent cross-project substrate. Two of the five bets are structural:

- **F2** rewires the dispatch tree (specialists can hand raw output to *each other*, not only back through the master) — a doctrinal change to PRISM's orchestration model.
- **F4** introduces a **semantic cross-project knowledge index** — a new persistent subsystem (storage + embedding + query + sync) that didn't exist in v4.x and that other v5.0 bets build on.

The thesis: **v4.x made Claude Code self-aware about complexity; v5.0 makes it self-improving across projects.** The verdict-regression scanner (A5) learns from accumulated review history; the semantic index (F4) lets a specialist in project B benefit from a decision logged in project A; SARIF output (C4) makes PRISM's reviews CI-gateable so regressions are caught by machines, not memory.

Because the structural bets need design passes, **this document is a roadmap, not a 40-task plan.** It scopes each bet enough to sequence them and to start the F4 brainstorm — which is the critical path.

## The five bets

| ID | Bet | Type | Depends on | Rough effort |
|----|-----|------|-----------|-------------|
| **F4** | Semantic cross-project knowledge index | New subsystem (foundational) | v4.6 telemetry + KB infra | Large (weeks) |
| **A5** | Verdict regression scanner | New capability | **F4** (semantic index) + v4.6 C2 failure taxonomy | Medium |
| **F2** | Specialist-to-specialist raw output | Dispatch-tree redesign | independent (architectural) | Large |
| **C4** | SARIF / CI-gateable eval output | New output contract | v4.6 C1/C2 classifiers | Medium |

### F4 — Semantic cross-project knowledge index (THE foundational bet)

**What:** A persistent, embedding-backed index of PRISM's accumulated knowledge — decisions (`docs/prism/adjudications/`), lessons (`docs/prism/lessons/`), verdict logs, panel rationales, captured `/prism-clean` artifacts — queryable *across projects*, not just within the current working directory.

**Why it's foundational:** today PRISM's knowledge is per-project files. A decision adjudicated in `prism_3` is invisible to a session in `competition_agents`. F4 makes "have we solved something like this before, anywhere?" answerable. A5 (verdict regression) and a smarter SCOPE GUARD (deferred from v4.6) both need it.

**Rough approach (to pressure-test at brainstorm):**
- Reuse the existing KB infra (`tools/prism-kb-*.mjs` — indexer, query, classify, domains, notebook-init already exist). F4 extends from per-project to a global `~/.claude/.prism-kb/` index with project-provenance tags.
- Embedding backend decision is the central open question: local model (no network, slower, privacy-preserving — matches PRISM's no-API-key posture per [[feedback-prism-claude-p-auth-pattern]]) vs. a hosted embedding API (faster, needs a key — conflicts with the subscription-only auth model). **Recommend local embeddings** to stay consistent with PRISM's privacy + no-key stance.
- Query surface: extend `/prism-recall` (already the unified-recall command) with a `--cross-project` mode.

**Design questions for its own brainstorm:** embedding model + storage format; provenance + privacy (do you *want* project A's secrets surfacing in project B?); index freshness/sync (this absorbs the v4.6-deferred E1 index-freshness item); opt-in vs default; index size/cost ceiling.

### A5 — Verdict regression scanner

**What:** Detect when a class of review verdict that used to pass starts failing (or vice-versa) — "specs in domain X started getting UN-CITED at 3× the prior rate after commit Y." A regression detector for *review quality*, not code.

**Why it needs F4:** meaningful regression detection needs a semantic notion of "similar verdicts across time and projects," which is exactly what F4 provides. Built on per-project verdict logs alone it's too narrow.

**Also needs:** v4.6's **C2 failure-mode taxonomy** (so regressions are categorized by *why*, not just count).

**Rough approach:** periodic (or on-demand) scan of the verdict log + semantic index; flag statistically-significant shifts in failure-mode distribution per domain/spec; surface via `/prism-recall` or a new `/prism-regression` report.

### F2 — Specialist-to-specialist raw output (dispatch-tree redesign)

**What:** Today every specialist returns to the master, which synthesizes. F2 lets specialists pass raw output *directly to each other* for chained/pipelined work, with the master as supervisor rather than sole hub.

**Why it's a major:** this changes PRISM's core orchestration doctrine (the "dispatch through master" invariant that the mutation-guard, parent-dispatch-guard, and parallel-guard all assume). Those guards would need rethinking. High blast radius.

**Why it's valuable:** some multi-step work is genuinely a pipeline (A produces an artifact B refines C validates) and forcing every hop through the master adds latency + context-copying overhead.

**Design questions for its own brainstorm:** how do the existing dispatch guards adapt? how is the master kept in the loop for review without being the data-bottleneck? how does Phase 1.5/0d OOB review work when output never passed through the master? **This is the riskiest bet — recommend it as its own parallel track, not bundled with F4.** It may even warrant being its OWN major (v6) if the redesign is deep.

### C4 — SARIF / CI-gateable eval output

**What:** Emit PRISM's review verdicts (panel quality, Phase 1.5, Phase 0d) in [SARIF](https://sarifweb.azurewebsites.net/) so they can gate CI — a failing review becomes a red check, not a notice a human might miss.

**Why it needs v4.6:** SARIF needs structured, classified findings — exactly what v4.6's **C1 validation classifier + C2 failure taxonomy** produce. Without them you'd emit unstructured prose into a structured format.

**Rough approach:** a `tools/prism-sarif-export.mjs` that reads verdict logs + classified findings and emits SARIF 2.1.0; a GitHub Action snippet in the docs. Smallest, most independent bet — could even ship as a v4.7 minor if the v5.0 timeline stretches.

### E4 — MEMORY.md governance / drift control

**What:** Lifecycle management for the auto-memory system (the `~/.claude/.../memory/` MEMORY.md + entries this very session writes to). Detect stale memories, contradictory entries, unbounded growth; propose consolidation/retirement.

**Why it's a major-adjacent subsystem:** memory currently grows monotonically with no governance. As it scales, stale/contradictory entries degrade recall quality. E4 adds the "is this memory still true?" loop that the memory-system instructions gesture at but don't enforce.

**Rough approach:** a `/prism-memory-audit` that scans memory entries for staleness signals (referenced files/flags that no longer exist — the same "verify before recommending" check the memory system already prescribes), contradiction detection (two entries asserting opposite rules), and size pressure; proposes retirements for approval. Independent of F4 but would *benefit* from F4's semantic similarity (contradiction detection is easier with embeddings). Could be standalone.

## Dependency graph + recommended sequencing

```
                 v4.6 (calibration + C1/C2 classifiers + telemetry data-quality)
                        │
        ┌───────────────┼────────────────────────────┐
        ▼               ▼                             ▼
       F4  ─────────►  A5                            C4
  (semantic index)  (verdict regression)      (SARIF, needs C1/C2)
        │
        ▼
  (smarter SCOPE GUARD,
   cross-project recall)

   F2 (dispatch redesign) ── independent, highest-risk ── possibly its own major (v6)
   E4 (memory governance) ── independent, benefits from F4 ── could be standalone minor
```

**Recommended order:**

1. **v4.6 first** (separate spec) — its C1/C2 classifiers + telemetry are prerequisites for A5 and C4; ship it as a normal minor.
2. **F4 brainstorm → design → build** — the foundational bet; everything downstream waits on it. Start here for v5.0 proper.
3. **A5** — once F4's index exists, A5 is a medium build on top.
4. **C4** — independent of F4; can run in parallel or slip to a v4.7 minor if you want a CI win sooner.
5. **E4** — independent; schedule opportunistically; lighter if F4 lands first.
6. **F2** — treat as its own track. Given its blast radius on the dispatch guards, it may deserve to *be* v6 rather than ride in v5.0. Decide after F4.

**Minimum viable v5.0:** F4 + A5 (the "self-improving" core). C4/E4/F2 can be staged across v5.x point releases or split out.

## Entry criteria for starting v5.0

| Criterion | Why |
|---|---|
| v4.6 shipped + tagged | C1/C2 classifiers + clean telemetry are prerequisites |
| v4.5/v4.6 installed + accruing real cross-session data | F4's value + A5's regression baseline need actual history |
| F4 brainstorm completed with embedding-backend decision locked | F4 is the critical path; its central open question (local vs hosted embeddings) gates everything |
| A go/no-go on F2-as-v6 | Decide whether the dispatch redesign rides v5.0 or splits to its own major, so v5.0 scope is bounded |

## What v5.0 is explicitly NOT

- Not another additive-polish minor — if the candidate list collapses to "more small items," that's a v4.7, not v5.0.
- Not buildable without F4's design pass — do not start coding A5 or a cross-project SCOPE GUARD before the semantic-index brainstorm locks the storage/embedding model.
- Not a place to smuggle v4.6-deferred items (E1/E2/G1/C3) — those are minors.
